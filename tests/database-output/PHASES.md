# Original database phase profiles

The original fourteen models in `models.toml` remain unchanged. The additive
`phases.json` suite tests complete transcripts, logical table/cache statistics,
status, stderr, ordered effects, full filesystem state, bounded execution, and
GNU repeat stability. `--suite core` selects the original fourteen,
`--suite phases` selects the additive inventory, and `--suite all` selects both.

The phase hypotheses were written before GNU discovery. Full transcript
expectations are explicitly derived afterward from independently qualified GNU2
runs; their provenance is retained rather than presented as independently
predicted bytes. There is no exemption for counters, missing sections, changed
origins, branch order, error text, or extra dumps. Each dump has separate indexed
clock slots. Directory identities come from predetermined fixture paths sampled
outside the child, and repeated slots must refer to the same captured identity.
Clocks must lie within independent libc `time(NULL)` bounds, without tolerance.

The fixtures cover assumed old/new ages; distinct double-colon automatic scopes,
results and final timestamps; actual pipe-jobserver children; native setup and
process finalizers, including reader failure; generated includes and restarts;
recursive children; early CLI evaluation and chdir failure; late reader/recipe
`-p`; shared target-specific/automatic tables; preserved strong local flags; and
post-update deletion with and without VPATH. Native fixtures are original C
sources with manually declared API signatures and compile once before any
engine runs. Compiled fixture bytes and hashes participate in the full
filesystem comparison. Expected deletions name declared input files and change
only the expected final snapshot; setup never deletes those inputs early.

The first native inputs used randomized absolute module paths. Their lengths
changed literal string-cache byte totals, so that input/template combination
was not portable across temporary roots. The original inputs, GNU2 observations
and failed transformed comparison remain retained. A fixed `./probe.so` spelling
was selected before fresh GNU2 discovery; no variable statistic slots or output
normalization were added. Absolute-load database history remains a separate
future profile requiring a fixed owned path.

`phase-history-v1` preserves the initial twelve plans, native input refinement,
first target-scope discovery, observer/tool errors and the first failing
integration checkpoint. Later `phase-history-v2` extends that record without
rewriting it. The `qualification-phases28` checkpoint retains the first frozen
development and optimized 28/28 result and its coherent source/build inputs.
The final `qualification-phases33` checkpoint retains all 33/33 complete
profiles in both builds, the coherent 86-input source closure, and both-build
native221/debug64/directory40/JOBS9 regressions. Workspace628 Rust units,681
tooling controls and strict Clippy pass in the combined development checkout
(the tool count includes eleven separate optional-component controls). Subsequent state and strong-local
controls have their own pre-observation plans and preceding-candidate failures. Passing deletion controls
did not reproduce an initially suspected stale timestamp fallback; they justify
retaining the ownership behavior rather than making a speculative change.

These finite profiles do not establish the complete database surface, M3/M6,
or performance parity. Wider asynchronous/loaded-module interactions, early
help/version cosmetic slots, enabled Guile, non-C locales, resource boundaries,
and real projects remain explicit follow-up work. Formatting only reads saved
state: it never replays expansion, assignments, includes, search, or stat calls.
