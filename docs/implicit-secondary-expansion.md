# Implicit candidate secondary expansion

Implicit search now evaluates deferred prerequisites while deciding whether a
candidate is viable. The independent core lexer retains nested make references
inside a word; the Linux engine expands one word, parses its filenames and checks
its dependencies before proceeding. A missing prerequisite skips later words and
their shell/file/eval/message effects. Effects in the current word finish before
its resulting filenames are checked. Rejected candidates never install build
rules or intermediate flags; their expansion effects remain observable.

## Stems and automatic variables

Keep deferred bytes intact during pure candidate construction. Replace the first
percent per whitespace word with a simple automatic stem reference during search,
so dollar bytes inside stems cannot undergo an extra expansion. For slashless
target patterns, use the stem basename and reconstruct the original directory on
each resulting prerequisite only when the unexpanded word contained a percent.
Percents generated by variable expansion remain literal. Normalize leading `./`
components before directory reconstruction, including ordinary immediate rules.
Archive member-only and complete archive patterns keep their existing separate
search order and member spelling.

The first deferred word initializes automatic variables from the target's known
explicit prerequisites. Later words do not acquire earlier implicit dependencies.
Candidate transitions update the stem without rebuilding the other automatic
values. Preserve normal/order-only transitions, duplicate-role promotion and `-B`
behavior. Search diagnostics use GNU's program-level context, including for rules
in included files; they do not use the candidate recipe's source line.

Target metadata is observed before candidate expansion. A function creating or
removing the target during search does not reverse GNU's earlier freshness
observation. Low-resolution comparisons and warnings also precede those effects;
recipe execution retains its existing timestamp refresh and cleanup behavior.
Regression fixtures cover creation/removal, query/dry modes and warning/error
ordering with anchored times.

## Scope and file lifecycle

Root searches retain the first requesting parent's inherited variables. Temporary
intermediate searches use globals and pattern bindings, without borrowing the
parent or the real target's explicit bindings. A selected chain retains its
activated pattern scope, then layers it onto the real parent's context when the
file is built. This prevents repeating effectful pattern assignments while
preserving recipe-time inheritance and explicit target variables. Rejected
chains discard temporary scopes.

A generated prerequisite is explicit when its unexpanded word had no percent.
Retain these flags when committing a selected plan, before choosing intermediate
cleanup roles. For example, `$$*.mid` can keep a generated file that `%.mid` would
remove. Glob results use NUL-separated names so blanks and arbitrary filename
bytes survive selection. Unmatched patterns retain their original spelling.
Ordinary literal names avoid the glob boundary entirely.

Only retry GNU's older ought-to-exist policy after encountering a file mentioned
elsewhere or as a command-line goal that does not qualify under normal selection. Record prerequisites
whose recursive search proved impossible, and cancel affected candidate retries.
Preserve unrelated mentioned files for compatibility search. These observations
last for the invocation and clear on Makefile restart. They reproduce GNU's
search behavior, including a later effect creating an already rejected file;
they are not a persistent dependency cache or a cache of file timestamps.

## Coverage and remaining scope

Add 102 original required fixtures for word/effect order, rejected/successful and
terminal candidates, multi-level chains, explicit/implicit automatic variables,
private/inherited/target/pattern scopes, activated-scope lifetime, eval, shell,
file writes, byte/dollar/directory stems, globs, archives, grouped peers, include
restarts, execution modes, compatibility fallback and impossible-file reuse.
The preceding main build fails 99 of these fixtures and passes three.
Four core tests exercise the independent lexer and stem-reference boundaries.
A seven-step stateful scenario verifies no-op/query builds, anchored timestamps,
removal/restoration of inputs and fresh candidate priority on each invocation.

The corpus now contains 2,984 cases: 2,972 required matches and 12 existing
pending mismatches. Stateful coverage is 51 scenarios / 140 invocations. No
upstream implementation or tests were copied; GNU 4.4.1 served as the behavioral
reference. M4 remains open for GPATH/permanent renaming, wider file-record aliases,
the remaining archive-format/runtime matrix and broader real-project acceptance.
This ledger is not an exhaustive compatibility inventory.

## Performance measurements

Avoid allocating boxed word iterators or cloning complete recipes for rejected
candidates. The ordinary-rule path retains its compact dependency representation;
only candidate construction records which immediate dependencies used a stem.
Explicit rules with recipes return without an unnecessary clone.
Shared explicit/implicit automatic-value preparation retains the existing
empty-ready-list fast path.

`make bench-compare BENCH_SUITE=implicit-rejections BENCH_REPEAT=101` compares
64 explicit empty targets against 64/256 matching rejected rules, with no
expansion effects or child commands. Both the prior build and current build
produce GNU's exact output and status on these workloads. A local paired run
against preceding main `e616601` measured:

| Workload | rmake (ms) | Previous rmake (ms) | GNU 4.4.1 (ms) |
| --- | ---: | ---: | ---: |
| 64 rejected rules | 3.054 | 8.933 | 1.298 |
| 256 rejected rules | 14.119 | 78.757 | 3.493 |

These selected rejection workloads improve by about 2.9x/5.5x by avoiding
unneeded compatibility retries and reusing GNU's impossible-file observations.
GNU remains faster. Existing 400-target lookup controls measured 1.670/2.183 ms
(previous 1.611/2.233 ms; GNU 0.942/1.373 ms). These small absolute costs remain
visible; this change does not establish general lookup speed parity.

A separate 101-sample core run measured startup at 0.691 ms (previous 0.665 ms),
10,000 no-op targets at 28.385 ms (28.578 ms), and expansion at 4.606 ms
(4.605 ms). GNU measured 0.613, 11.600 and 2.762 ms respectively. These small
core differences are not presented as improvements.

All campaigns use alternating paired engine order, identical arguments/path/
environment and exact output checks, including startup, two warmups per engine
and warm OS caches. Runs were sequential outside functional validation. There
is no CPU isolation, confidence interval, CPU/RSS/I/O profile or cold-cache
acceptance evidence. Raw samples and binary identities remain in ignored
`artifacts/bench/implicit-rejections-101.json`,
`artifacts/bench/implicit-secondary-core-101.json` and
`artifacts/bench/implicit-secondary-search-101.json`. M8 remains unfinished;
no persistent graph cache was introduced.
